# Report interpreter startup failures before WebDriver timeouts

Tracking issue: [#132](https://github.com/xpqz/tauride/issues/132).

An interpreter startup failure opens a synchronous native error dialog. While that dialog is open, the page cannot answer ordinary WebDriver requests, so the harness previously reported an opaque element or script timeout and discarded the useful evidence during cleanup.

## Diagnosis

The investigation captured a real recurrence with the app alive and the main thread inside `sync_dispatch → dialog::message → NSAlert::runModal`, entered through WebKit's synchronous URL-scheme handler. The alternative DirectEval channel also timed out. This was a native modal blocking JavaScript, not evidence of a lost WebKit evaluation callback.

After adding test-build dialog logging, the next recurrence reported **Interpreter exited with code 138**. The matching macOS reports show Dyalog 21.0 crashing during Session loading (SIGBUS, with a related crash-dump child). The preceding recurrence coincided with a Dyalog CEF/TCC SIGTRAP during initialization. The three original #132 failures also coincide with these two crash families; their older logs lack owned PIDs and dialog text, so that correlation is supporting evidence rather than exact ownership proof.

The test harness does not repair either interpreter defect. It disables Dyalog's unused embedded Chromium by default (`ENABLE_CEF=0`), while preserving an explicit override. The Dyalog configuration reference (`docsearch -r 879`, Enable_CEF) documents that this disables HTMLRenderer; it does not disable Tauride's own webview. The current native suite does not exercise HTMLRenderer. Session-loading crashes are a distinct observed family, and the available evidence does not establish that CEF causes them.

## Behaviour

Test builds record a bounded, structured description before opening native message dialogs. Startup reports unexpected dialogs with their actual error text and retains its phase, timing, owned app PID and last delivered frontend snapshot. Failures retain a bounded read-only frontend probe, app output and a macOS sample of the live owned process before teardown. Diagnostic failure cannot replace the original error or prevent cleanup.

Readiness uses ordinary WebDriver and retains the requirements for a loaded page/window manager, dismissed splash, active IDE tab and ready Session model. Connection-screen tests require only the first two. No process restart, dialog dismissal or retry of a failed startup conceals an interpreter crash. Native dialog behaviour and production interpreter settings are unchanged.

Snapshots contain readiness, connection-screen and main-page dialog visibility, and geometry metadata, without editor source or environment values. Test-only native dialog records whitelist and bound their title, message, detail, buttons and identifiers. Retained diagnostics live outside the temporary profile, which is still removed.

## Validation

The pull request records final test totals and CI results. Investigation evidence includes:

- The instrumented baseline passed 40 consecutive launches and all 86 native tests, demonstrating why a clean run alone could not diagnose the intermittent failure.
- The proposed alternate transport passed 40 launches but then failed in the full suite (85 passing cases, one startup hook failure). Its thread sample exposed the native modal. The workaround did not address the diagnosed native modal and was removed.
- With dialog logging enabled, launch 9 captured the interpreter exit message and matching crash reports.
- With unused CEF disabled, 80 consecutive launches passed, each followed by ordinary WebDriver execution.

Local validation uses macOS 27.0.1 and Dyalog 21.0.54424. The underlying interpreter crash reports are outside Tauride's implementation; future interpreter failures must remain visible test failures with useful diagnostics.
