# Explain errors with Claude Code

Implements [Tauride #147](https://github.com/xpqz/tauride/issues/147). Branch `claude/147-claude-provider`; implementation commit `8822bd61`.

Adds a `claude` error-explanation provider behind the provider interface from #146. Each explanation runs one isolated `claude -p` process with no tools, no MCP servers, no user or project settings, no slash commands or skills and no session persistence. The provider streams its text deltas into the panel. The setup check reads `claude auth status --json` and starts no inference. The flags and stream handling are recorded in `tauri/agent-providers.md`, measured against Claude Code 2.1.301.

## Files

- `src-tauri/src/companion/claude.rs`: the provider and its tests.
- `src-tauri/src/companion.rs`: registry entry; executable search per provider (`ExecutableSearch`, used by Codex and Claude Code with unchanged Codex locations and messages); `PrivateDir`, the per-process empty working directory, now shared by the Codex server.
- `src-tauri/tests/fixtures/fake-claude.py`: a deterministic print-mode and `auth status` double that records argv, stdin and working directory.
- `tauri/agent-providers.md`: the `claude` section, from measurement.
- `tauri/agent-pairing.md`: user documentation for the Claude Code provider.

| `claude_setup_reads_auth_status_only_and_reaps_every_outcome` | `loggedIn` → `ready` or `signin`; malformed output and timeout → `unavailable`; missing executable → `missing`; no `-p` invocation; no account detail in the result; every probe process reaped. |

## Design decisions

- One process per request, never reusable. The session's `stop` for a non-reusable provider kills and reaps the child, so the provider does not release it again after a successful request.
- The child is registered in the session's owner immediately after spawn, before any I/O, so cancellation and session close reach it at once.
- `init` is checked at run time: any tool or MCP server listed there fails the request, and so does an `init` without those fields, with a message asking to update Claude Code. This, the flags and the `tool_use` checks back `enforces_no_tools: true`.
- Text is taken only from `text_delta` stream events; `result.result` is used only when no delta arrived. `is_error` decides failure, whatever `subtype` says. A missing `is_error` counts as failure.
- Errors from the service and the first stderr line are capped at 1 KiB and 4 KiB of stderr is kept; the rest is drained so a chatty process cannot block.
- `--model=<m>` is one argument, so a model beginning with `-` stays a value; measured: `--model=--tools=Bash` is rejected by Claude Code as an unrecognised model.
- `--bare` is not used: it never reads the claude.ai sign-in.

## Live run

Through the provider code (a temporary ignored test, not committed) against Claude Code 2.1.301 with the claude.ai sign-in, the account's default model (not recorded), and no `ANTHROPIC_API_KEY`. Both explanations were correct for the supplied evidence. Not through the Tauride UI; the panel path is the same as Codex's and is exercised by the existing native tests with the Codex fixture.

| Request | First streamed text | Completion |
| --- | ---: | ---: |
| LENGTH ERROR, `1 2 3+4 5` | 5.19 s | 9.09 s |
| VALUE ERROR, undefined `foo` | 3.82 s | 9.20 s |

Two observations each, not a latency claim. Every request starts a new process.

## Noted

- `companion::tests::provider_setup_finishes_and_reaps_independently_after_session_close` (Codex) fails intermittently on unmodified `main` (1 of 6 runs there, also seen once on this branch): its 3 s wait for the fixture's pid file can elapse on the first run after a build.
- `cargo clippy --tests` reports `type_complexity` at `companion.rs` `RegistryEntry::create` and `Session::active`, both present on `main`; the crate is not clippy- or rustfmt-clean and this change does not reformat it.
- Frontend unchanged: Preferences and the panel already list providers from `companion_providers`; the Node unit suite was not run.
