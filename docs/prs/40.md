# #40: Start an indented label token at its first character

An indented `End:` label in a class method started its `meta.label.apl` token one character late. With ten leading spaces, the whitespace token covered `E` and the label token began at offset 11. Spacing before the colon shifted the boundary further.

`src/mon_apl.js` now emits the label token before consuming the colon separator. The consumed width is unchanged, so following whitespace and code keep their positions. Dfn guards and array notation retain their existing handling.

`tests-node/labels-completion.js` calls the actual registered tokenizer and checks leading whitespace, every label character, and following code at indentation widths 1, 4, and 10, with zero, one, and two spaces before the colon. It also covers unindented labels, ordinary names, dfns, and array notation. The indented label is a noninitial token: first-token normalization cannot conceal the wrong boundary in those checks.

Tests were written and reviewed before implementation. The combined #40/#41 baseline had 15 failing tests and 16 passing controls; ten failures checked label starts. After the two minimal fixes, `node --test tests-node/labels-completion.js tests-node/language.js` passes all 40 tests. `git diff --check` passes for the changed source and regression file. Source ESLint reports the same existing diagnostics as the saved worktree baseline, with none added by this change.

Real Monaco tokenization in the native Tauri webview starts the label at offset 10 for both the minimal class and the original upstream workspace source. Following code in the minimal class keeps its expected token positions. Native results are recorded in `/private/tmp/tauride-36-41-native-results.json`. The screen was locked; physical keyboard delivery and visual colours were not verified. The full 99-test unit suite, `test:build`, and browser zf smoke check pass.
