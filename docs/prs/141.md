# Start without a splash or unused helper windows

Tracking issue: [#141](https://github.com/xpqz/tauride/issues/141).

Startup used to create Preferences, interpreter dialog and Status Output webviews,
then wait for all three to register over IPC before opening the connection screen
or starting an interpreter. The splash covered that wait. Startup now waits only
for the session's IPC listener and opens the requested screen directly.

Each session creates a helper on its first request and reuses it afterward.
Concurrent requests share creation and wait for that helper's registration.
Preferences receives current settings before opening the requested tab; Status
retains output in arrival order, including when automatic display is disabled.
Interpreter dialogs are queued and replies remain with their owning session.
Closing a session cancels its outstanding dialogs. Failed helper creation is
reported, the window is destroyed, and a later request can retry.

The splash markup and styles are removed from both desktop and browser builds.
Browser Preferences and dialogs keep their existing in-page behaviour. Existing
menus, shortcuts and the public helper handles remain available.

## Validation

The new tests failed against the original eager startup before implementation.
Unit regressions cover shared creation, registration identity, initial state,
ordered delivery, failed creation/retry and stale interpreter ownership. Native
regressions cover startup window counts, first/repeated use, rapid requests,
pending Status visibility, concurrent sessions and closing an owner during first
dialog creation. Existing Preferences tests now request the helper before waiting
for its socket. Linux connection CI includes the first-use Preferences regression.

- `npm run test:unit`: 305 passed.
- Full native suite on macOS: 104 passed in one run, including nine new cases.
- Browser build and headless Chrome smoke: passed, no console errors or missing
  assets; Monaco worker and folding checks passed.
- Window-specific screenshots of Connect, Session, first-use Preferences and
  first-use Status Output were inspected. Layout and controls remained usable.
- Independent implementation review found no remaining blocker. Native runs
  verified first-use IPC delivery order and initial helper theme.
- Process inventory after the full suite had no additional Tauride/Dyalog
  processes; all 30 pre-existing interpreter/helper processes remained present.

String-dialog native tests inject the protocol handler and intercept its reply;
they exercise real helper webviews and IPC, without claiming that the interpreter
emitted those test requests. Physical UI checks were on macOS; Linux connection
tests and platform builds run in CI.

## Startup comparison

Measured on Apple silicon, macOS 27.0.1, with Dyalog 21.0.54424. Both executables
used the same debug profile and `ui-tests` feature. The baseline was built from
`36466c1e313ab0a0793ec980c916a6a8f1deaae9` before production edits; the candidate
contains this change. Each executable embeds its own staged frontend.

For each scenario, one warm-up per executable was followed by five launches per
executable, alternating before/after order between rounds. Every launch used a
fresh isolated profile and exited before the next launch. Both variants used the
same frozen baseline `test/_tauri.js` harness. Timing began at its `spawn app`
phase and ended after an explicit visible-Connect or connected-Session/prompt/
model/layout check. Window counts were collected after the timing endpoint.

| Scenario | Before median (range) | After median (range) | Median reduction |
| --- | --- | --- | --- |
| Connection screen | 1,083 ms (1,058–1,170) | 762 ms (746–793) | 321 ms / 29.6% |
| Automatic Dyalog session | 1,534 ms (1,427–1,569) | 1,082 ms (1,080–1,104) | 451 ms / 29.4% |

All measured baseline launches had four webviews; every candidate launch had one.
These are **harness-observed readiness times**, including port setup, WebDriver
startup and polling. They are a small comparative sample with warmed caches, not
production cold-start measurements or a guarantee for other machines. Helper
initialization cost moves to first use.
